## 1. Architecture

Single Next.js app. Route handlers **are** the API — there is no separate backend.

```
src/
  app/
    (app)/       signed-in surfaces: home, sell, chats, saved, settings, profile,
                 requests, notifications, search
    (auth)/      login + onboarding
    (admin)/     hidden panel, mounted on an env-configured dynamic segment
    api/         all 41 route handlers
    listing/     PUBLIC listing pages (shareable without an account)
    legal/       terms + privacy
    offline/     PWA offline fallback
  components/    ui primitives, then feature folders (listing, chat, sell, admin…)
  lib/           server helpers; lib/client/* is browser-only
  proxy.ts       edge middleware (see §2 — renamed from middleware.ts)
```

### Key design decisions

| Area | Decision | Why |
|---|---|---|
| Auth | Phone OTP primary; verified VIT email adds a badge | Account is keyed on a verified number |
| Tokens | 15-min JWT access in httpOnly cookie; opaque refresh stored hashed, rotated | Reuse of a rotated token is detectable as theft |
| CSRF | Double-submit: `proxy.ts` sets a JS-readable cookie, client echoes `x-csrf-token` | All 31 write-route files go through `mutation()` |
| Realtime | SSE at `/api/realtime`, in-process pub/sub | Correct for one instance; swap `lib/realtime.ts` for Redis to scale |
| Storage | Local disk behind an S3-shaped driver | Magic-byte verified, sharp re-encode strips EXIF/GPS, content-addressed |
| Search | Postgres pg_trgm | Typo tolerance without an external search service |
| Money | Stored as **paise** (integers) | No float drift |

## 3. The two things worth understanding

### Phone numbers (the privacy core)
A number is **never** on a profile or listing. Flow:
1. Buyer requests it on a specific listing.
2. Seller approves or rejects **that specific request**.
3. Approval is scoped to **one listing** — approving someone for a cycle is not
   consent to be called about everything else.
4. Seller can revoke at any time.

Exactly one route returns another user's number:
`GET /api/user/[userId]/phone?listing=<id>`. It re-checks the grant on every call.
**Every denial returns an identical 403**, so the response cannot distinguish
"never asked" / "was rejected" / "was revoked".

### The admin panel
- Never linked, never in the sitemap, and **deliberately absent from robots.txt**
  (a `Disallow` rule would publish the one thing it relies on staying unguessable).
- A wrong path 404s identically to any other miss.
- The hidden path is **obfuscation, not the boundary**. The real boundary is that
  every `/api/admin/*` route requires a live admin session.
- Admins created only via `npm run admin:create` (interactive, scrypt hash).
  Credentials never in env or code.
- **Reading a reported conversation** is the most invasive capability, fenced 4 ways:
  MODERATOR+; a report must exist and name a conversation; the 30-day moderation
  window must be open; and a `ChatAccessLog` row is written **before** messages are
  returned — a read cannot happen without a trace.

## 4. OTP delivery (5 channels)

`OTP_SMS_PROVIDER` selects the driver; all implement one `OtpProvider` interface
in `src/lib/otp/providers.ts`.

| Value | Channel | Notes |
|---|---|---|
| `console` | terminal | **Dev default.** Prints the code; returns `devCode` in the API response so the login screen shows it. Gated on `NODE_ENV !== 'production'`. |
| `whatsapp` | Meta Cloud API | **Recommended for India.** No TRAI DLT paperwork. |
| `msg91-whatsapp` | WhatsApp via MSG91 | MSG91 handles Meta verification — the slow part of going direct. |
| `msg91` / `fast2sms` | SMS (India) | Requires TRAI DLT registration. |
| `twilio` | SMS (global) | Simplest start, priciest in India. |

**WhatsApp setup** — Meta forbids free-form OTP, so create a template in WhatsApp
Manager with category **Authentication**, then:
```
OTP_SMS_PROVIDER="whatsapp"
WHATSAPP_PHONE_NUMBER_ID="..."
WHATSAPP_ACCESS_TOKEN="..."     # permanent System User token, not the 24h test one
WHATSAPP_TEMPLATE_NAME="campuscart_otp"
```
Non-obvious: the code is sent as **both** a body parameter and a button parameter.
The copy-code button reads it from the button param — omit it and the button
copies nothing.

**Production env guards** (`src/lib/env.ts`, `superRefine`): the app refuses to
boot if `OTP_SMS_PROVIDER=console`, if the selected provider is missing
credentials, or if `ADMIN_PANEL_PATH` is still the repo default. Skipped during
`next build` (`NEXT_PHASE === 'phase-production-build'`) so Docker/CI can build
without secrets. Verify with `npm run env:check`.

## 6. What was verified (and how)

Ran the app against a live Postgres and tested with real HTTP — not just compile.

**Security properties**
| Test | Result |
|---|---|
| `/admin`, `/administrator`, `/wp-admin`, `/dashboard` | **404** |
| `/{real-panel}/dashboard` without session | **307** → login |
| `/{real-panel}/login` | **200** |
| `/home` `/sell` `/chats` `/settings` logged out | **307** → login, `?next=` preserved |
| Write with no CSRF header | **403** |
| Write with wrong CSRF token | **403** |
| Write with valid token | passes |
| Cross-site `Origin: https://evil.example.com` | **403** |
| All `/api/admin/*` without session | **401** |
| CSP, HSTS, X-Frame-Options, Referrer-Policy | present |
| Admin pages `X-Robots-Tag: noindex` + `no-store` | present |
| Panel path in client code / robots / sitemap | **absent** |

**Full user flows**
- Signup: OTP request → verify → onboarding → session cookies issued
- Posted a listing; confirmed it appears in feed, search, and detail page
- Second user (buyer) → made an offer → **seller sees it in chat with
  accept/counter/decline** → accepted → system message appended
- Email verification → VIT badge granted (`isVitVerified: true`)
- Pickup area: created an `OUTSIDE_CAMPUS` listing; filter returns exactly it
- Typo search: "chargr"→charger, "batery"→battery, "thnkpad"→ThinkPad; nonsense → 0
- Shared listing link renders for a logged-out visitor

**NOT verified**: no headless browser was available, so dark/light rendering,
animations, and responsive breakpoints were never seen. Markup and status codes
only. **Check on a real phone before showing students.**

## 7. Post-launch fixes (the 6 user-reported items)

### 1. Email verification from profile ✅
Phone-signup users had no way to add an email → no way to earn the VIT badge.
- New `src/components/settings/email-verification.tsx` — send code, enter code,
  badge granted if domain matches `VIT_EMAIL_DOMAIN`.
- API already existed (`/api/auth/email` POST/PUT); this was purely missing UI.
- Settings page now passes `vitDomain` (server-only env) down to the form.
- **Verified**: added `@vitbhopal.ac.in` address → `isVitVerified: true`.

### 2. Splash / launch animation ✅
`src/components/brand/splash-screen.tsx`, mounted in root layout.
- Cart draws itself stroke-by-stroke (`pathLength` 0→1), wheels spring in,
  then "CampusCart" + **"Dedicated Marketplace for VIT Bhopal!!"**. ~2.2s.
- Plays **once per browser session** (sessionStorage, not localStorage).
- Skipped entirely under `prefers-reduced-motion`.
- `position: fixed` over the app — nothing is blocked on it finishing.
- New CSS token `--z-splash: 90`.

### 3. Inside/outside campus pickup ✅
Pickup was **inferred from the seller's role**, which was wrong in both directions
(a hosteller can meet off campus; a day scholar can meet at the gate).
- New Prisma enum `PickupArea { INSIDE_CAMPUS, OUTSIDE_CAMPUS }`, added to
  `Listing` with `@default(INSIDE_CAMPUS)` + index.
- Composer now has an explicit radio choice; the location fields switch on it.
- Buyers get filter chips in the filter sheet → **a day scholar can find
  day-scholar sellers with off-campus locations**.
- Shown on card + detail page.
- **Verified**: created an OUTSIDE_CAMPUS listing; both filters return correctly.

### 4. Hostel blocks 1A–8B ✅
Was wrongly `Block A`…`Block L`. Real scheme: 8 numbered blocks × A/B wings = **16**.
- `HOSTEL_BLOCKS` now generated: `1A 1B 2A 2B … 8A 8B`.
- Added `hostelBlockLabel()` → "1A" renders as "Block 1A" where the field label
  is absent (cards, profiles). Values starting with a letter pass through, so
  legacy data doesn't become "Block Block A".
- All 4 consumers (onboarding, composer, settings, filter sheet) updated.

### 5. Offers not appearing in chat ✅ *(the real bug)*
Root cause: the API correctly created a `kind: 'OFFER'` message, but
`message-bubble.tsx` had **no case for `OFFER`** — so it rendered an empty bubble.
The seller only ever saw the notification.
- Added real Prisma relations `Message.offer` / `Message.phoneRequest`
  (were loose `offerId` strings with no relation).
- Serializer now denormalises amount/status/`isMine` onto the message.
- New `src/components/chat/offer-card.tsx` — an **actionable card in the thread**:
  amount, % below asking, and accept/counter/decline **without leaving chat**.
- `reloadThread()` added to `chat-thread.tsx` refetches after a decision.
- **Verified end-to-end**: buyer offered ₹7,500 → seller saw
  `ACTIONS=accept/counter/decline` → accepted → `status=ACCEPTED` + system message.

### 6. Offers & Requests promoted to top nav ✅
Was buried in the profile dropdown, so sellers missed decisions.
- Desktop nav is now **Buy · Sell · Chats · Offers & requests** + profile menu.
- Mobile tab bar: Buy · Chats · Sell · **Offers** · You (Search dropped — it
  already has a permanent top-bar slot).
- New `pendingRequests` count on the session (pending offers + phone requests)
  drives a live badge.
- New `HandshakeIcon`.

## 8. Known issues / gotchas

1. **`npm run db:migrate` DOES NOT WORK.** The repo ships the trigram migration
   but **no baseline migration** that creates the tables, so `migrate` tries to
   index tables that don't exist. **Use `npm run db:setup`** (`db push` + indexes
   + seed). For production, generate a baseline first:
   ```bash
   npx prisma migrate diff --from-empty \
     --to-schema-datamodel prisma/schema.prisma --script > prisma/migrations/0_init/migration.sql
   ```
   Note is also in `scripts/db-indexes.ts`.

2. **ESLint is NOT installed.** The `lint` script (`next lint`) is vestigial and
   fails — `next lint` was removed in Next 16, and there's no `eslint.config.*`.
   To fix: `npm i -D eslint eslint-config-next` and add a flat config.

3. **Prisma client staleness.** After changing `prisma/schema.prisma`, run
   `npx prisma generate` **and restart the dev server** — a running server holds
   the old client and throws `Unknown field` at runtime even though tsc passes.

4. **`pkill -f "next dev"` kills the shell running it.** Use
   `ss -lptnH 'sport = :3000'` to find the PID instead.

5. **Sitemap logs 2 Prisma errors during build** when the DB is unreachable.
   By design — `sitemap.ts` has a try/catch that degrades to static routes. Build
   still exits 0.

6. **Dev OTP codes appear on screen.** Intentional and gated on
   `NODE_ENV !== 'production'`; production also refuses to boot with the console
   driver. Not a leak.

7. **Storage is local disk.** Single-instance only. Set `STORAGE_DRIVER=s3` and
   implement `S3Driver` in `src/lib/storage.ts` (interface + env vars already there).

8. **Realtime is in-process.** Single-instance only. Swap the two functions in
   `src/lib/realtime.ts` for Redis pub/sub — every caller already goes through
   `publish`/`subscribe`.

## 11. Deploy checklist

1. Provision Postgres; run `npm run db:setup` (or generate a baseline migration
   first — §8.1).
2. Set every required var; **change `ADMIN_PANEL_PATH`** (production boot rejects
   the default).
3. Set `NEXT_PUBLIC_APP_URL` to the real origin.
4. Configure a real `OTP_SMS_PROVIDER` — `whatsapp` recommended. Boot fails on
   `console` in production, so this can't be forgotten silently.
5. For >1 instance: move storage to S3/R2 and realtime to Redis.
6. `npm run admin:create`.
7. **Test on a real phone** — visual/responsive was never verified (§6).
